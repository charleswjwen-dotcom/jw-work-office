## 二、核心结论：可控性由「系统层」保证，而非 LLM 自律

T-S0-05 的关键命题是——**确定性工具不能被 LLM 绕过**。本 PoC 证明该保证落在系统层（Agent loop），与 LLM/提示词无关：

1. **工具契约层面**：`Tool.execute()` 的返回类型被约束为 `Promise<ChangeSet>`，工具物理上无法"直接改文件"——它只能构造变更描述。`replaceText` 即使命中替换，也只产出 `before/after` 文本载荷，原文档对象保持不变。

2. **Agent 拦截层面**：`enforceConfirmation()` 对任何"有变更但 `status !== 'pending'`"的 ChangeSet 强制改回 `pending` 并记录一条拦截。即便 LLM 被注入"status 设为 applied / 立即保存 / 跳过确认"，产出仍被拉回确认流程。

3. **失败降级层面**：工具抛错在 Agent 内被捕获，转为 `error` 字段完整（`code/message/recoverable`）的错误 ChangeSet，供 UI 展示且不使主进程崩溃。

一句话：**"是否落盘"的决定权永远不在 LLM 手里，而在系统确认流程手里。**

## 三、关键设计决策（供架构 v1.3 参照）

1. **确认强制点单一化**：`status='pending'` 是唯一"待确认"合法态；`enforceConfirmation` 是唯一裁决入口（Agent 层），工具无权自设终态。这为 S2 的 ChangeSet + diff 交互提供了不可绕过的信任基线。

2. **Mock 先行，Key 后补**：以 `MockChatProvider`（实现 `ChatProvider` 接口）驱动 function-calling 全链路，避开真实 API Key。真实 OpenAI/Anthropic Provider 只需实现同一 `chat(req): Promise<ChatCompletion>` 接口即可无缝替换，Gateway/Agent/Registry 均不改。

3. **LLMGateway 收敛非功能性关切**：重试（默认 2 次）、超时（默认 30s）、用量计量（`estimateTokens = chars/4`）集中在 Gateway，Provider 只管"一次对话"。

4. **zod 作为工具入参单一事实源**：`Tool.inputSchema` 既用于 Agent 侧 `safeParse` 入参校验（失败→`INVALID_INPUT` 错误 ChangeSet），又经 `zodToJsonSchema` 反射生成给 LLM 的 function schema，避免 schema 双写漂移。

5. **代码落点即 S2 产品底座（零返工）**：不同于 s0-01~04 的一次性 `poc/` 脚本，本 PoC 直接写入 `app/src/main`（llm/、tools/、agent/）与 `app/src/shared/agent.ts`，作为 S2 LLM 适配层/工具层/Agent 层的正式起点。

- **多工具编排未覆盖**：当前 loop 为单工具直调，多工具串联/并行与工具间依赖留待 S2 Agent 完善。

- 未触发任何兜底路径，LLM 工具调用可控性判定为**可落地**。
